# Полная перекраска веб-интерфейса: возможности и ограничения браузера и CSS

Research notes — browser and CSS mechanisms for comprehensively recoloring a third-party web application from an extension or injected script.

- Дата исследования / retrieved: **2026-09-22**
- Область: что можно и нельзя надёжно перекрасить из content script / расширения; сравнение подходов (переопределение селекторов, CSS custom properties, обход правил стилей, мутация CSSOM, сканирование computed style, MutationObserver).
- Конвенция: `[факт]` — подтверждено первоисточником (получено в этой сессии), `[спец]` — стандартное поведение платформы (спецификация/общепринятое знание, не перечитывалось в этой сессии постранично), `[рек]` — рекомендация/вывод автора заметок.

## 1. Какие CSS-свойства и механизмы рендеринга несут видимый цвет

### 1.1 Свойства, адресуемые через CSS `[спец]`
| Категория | Свойства | Перекрашиваемость чистым CSS |
|---|---|---|
| Текст | `color`, `text-decoration-color`, `text-shadow`, `caret-color`, `-webkit-text-fill-color` | Полная |
| Фоны контейнеров | `background-color`, `background-image` (градиенты), `background` (shorthand) | Полная |
| Границы | `border-color`, `border-{side}-color`, `outline-color` | Полная |
| Тени | `box-shadow` (цвет в значении), `text-shadow` | Полная |
| SVG | `fill`, `stroke`, `stop-color`, `flood-color`, `lighting-color` (это презентационные свойства, CSS переопределяет атрибуты) | Полная для inline-SVG; внешние `<img src="*.svg">` — только через `filter` |
| Графики-фильтры | `filter` (на элементе), `backdrop-filter` | Позволяет инверсию/сдвиг оттенка любых пикселей под элементом |
| Форм-контролы | `accent-color` (чекбоксы, радио, range, progress); `color-scheme`; стилизация `::-webkit-scrollbar*`, `::selection` | Частичная: нативные контролы (выпадающий список `<select>`, пикеры дат) частично вне контроля автора |
| Псевдоэлементы | `::before`, `::after`, `::placeholder`, `::selection`, `::marker`, `::-webkit-scrollbar*` | Полная через селекторы псевдоэлементов |
| Кастомные свойства | `--*` (CSS custom properties) — наследуются, могут нести цвета во всех вышеперечисленных | Ключевой рычаг, см. §3.2 |

### 1.2 Механизмы, НЕ адресуемые через CSS `[спец]`
- **Растровые изображения** (`<img>`, `background-image: url(...)`) — пиксели зафиксированы; CSS может применить `filter` ко всему элементу или подменить `background-image`, но не изменить пиксели.
- **Canvas** (`<canvas>`) — содержимое рисуется скриптом через 2D/WebGL контекст; перекраска возможна только (а) `filter` на элементе целиком, (б) перехват/перерисовка через инъекцию в page world.
- **Video/WebGL/WebRTC** — пиксели медиапотока; только `filter` на элементе или оверлей.
- **Тени/глубина, заданные растровыми спрайтами** (9-patch, PNG-тени) — только подмена/фильтр.
- **Content внутри `<iframe>` другого источника** — см. §2.3.
- **Контент, нарисованный в closed Shadow DOM**, доступен только пока есть ссылка на shadowRoot `[спец]` (см. §2.4).

## 2. Что достижимо из content script и где границы безопасности браузера

### 2.1 Изолированный мир content script `[факт]`
Источник: https://developer.chrome.com/docs/extensions/develop/concepts/content-scripts (получено 2026-09-22).
- Content script выполняется в **isolated world**: у него общий с страницей DOM, но отдельный глобальный JS-контекст; переменные страницы недоступны и наоборот.
- У content script полный доступ к DOM страницы: чтение/запись элементов, атрибутов, `style`, добавление `<style>`/`<link>` узлов.
- Content script может читать и модифицировать **стили и CSSOM того документа, в который он инжектнут**.

Вывод `[рек]`: для верхнеуровневой перекраски изолированного мира достаточно — внедрение `<style>` в `document.head`/`document.documentElement` работает. Для перехвата рантайм-страниц (например, патчить `CSSStyleSheet.prototype`, слушать `adoptedStyleSheets` до инициализации приложения) нужен **page world / MAIN world** инъекшен.

### 2.2 Инъекция стилей с каскадным приоритетом `[факт]`
Источник: документация Chrome `chrome.scripting.insertCSS` (поиск 2026-09-22): параметр `origin` принимает `"AUTHOR"` (по умолчанию) или `"USER"`.
- `origin: "USER"` помещает стили в **user origin** каскада. По порядку каскада CSS (спецификация cascade, `[спец]`) нормальные объявления из более позднего по приоритету источника выигрывают: user-origin нормальные объявления бьют author-origin, а `!important` автора бьёт `!important` пользователя, но нормальное `!important` user/UA стоит выше авторского `!important` в полном порядке: transition > UA !important > user !important > author !important > author normal > user normal > UA normal (в точном порядке по CSS Cascading spec `[спец]`).
- Практический эффект `[рек]`: инъекция с `origin:"USER"` позволяет перекрывать обычные авторские правила без `!important` в каждом правиле; против авторских `!important` всё равно нужен свой `!important` (author `!important` > user normal), либо стратегия из §3.
- Firefox-эквивалент: `css` инъекция через `scripting` API также поддерживает каскадный уровень (аналогичная семантика user/author origin `[спец]`).

### 2.3 Cross-origin: стили, фреймы, ресурсы `[спец]`
- **Cross-origin `<link rel=stylesheet>` / `@import`**: обращение к `cssRules`/`rules` такого `CSSStyleSheet` бросает `SecurityError` (same-origin policy CSSOM). Сами правила при этом **действуют** на страницу — их просто нельзя прочитать/переписать из скрипта.
  - Обход `[факт из кода Dark Reader]`: расширение с host permissions может выкачать тот же CSS через `fetch` (см. `loadAsText` в `style-manager.ts`) и разобрать текст самостоятельно, минуя CSSOM. Это стандартный приём.
- **Cross-origin `<iframe>`**: content script инжектится только в те фреймы, которые покрыты `matches` и (в манифесте) `all_frames: true`; содержимое фрейма чужого источника без собственного инжекта перекрасить нельзя, кроме `filter` на самом элементе `<iframe>` `[рек]`.
- **Шрифты, картинки** — можно перехватить/подменить через `declarativeNetRequest`/`webRequest` (уровень расширения, не content script) `[рек]`.

### 2.4 Shadow DOM `[спец + частично факт]`
- Правила из внешнего документа **не проникают** внутрь открытого/закрытого Shadow DOM, кроме:
  - наследуемых свойств (в т.ч. `color`, и **всех** `--custom-properties`) — custom properties наследуются через границу тени; это главный официальный канал темизации компонентов `[спец]`;
  - `::part()`/`::slotted()` — ограниченные, автором компонента разрешённые точки.
- `ShadowRoot` имеет собственный `adoptedStyleSheets` `[спец]`. Инжектнутый скрипт, получив ссылку на `shadowRoot` (для `open` — `el.shadowRoot`), может читать и переписывать эти таблицы.
- **Closed shadow roots**: ссылка доступна только в момент `attachShadow`; если её не перехватить (нужен MAIN-world патч `Element.prototype.attachShadow`), доступ теряется `[спец]`.
- `[факт из кода Dark Reader]`: `style-manager.ts` импортирует `iterateShadowHosts`, `watchForNodePosition` — движок обходит хосты теней и следит за позицией инжектнутых узлов; `index.ts` использует `getCSSFilterValue` — т.е. зрелый продукт комбинирует обход теней + фильтры, а не только селекторы.

### 2.5 AdoptedStyleSheets / constructible stylesheets `[спец]`
- `document.adoptedStyleSheets` и `shadowRoot.adoptedStyleSheets` — массивы `CSSStyleSheet`, созданных через `new CSSStyleSheet()`; модифицируются через `replace()`/`replaceSync()`/`insertRule()`.
- Content script может как **читать** (перечислять, читать `cssRules` — они same-origin по построению), так и **подменять** их.
- Приложение может пересоздавать массив в любой момент → нужен наблюдатель: `MutationObserver` **не ловит** присвоение `adoptedStyleSheets` (это не DOM-мутация) `[спец]`. `[рек]`: патчить сеттер/методы в MAIN world (`Object.defineProperty(document, 'adoptedStyleSheets', ...)`, обёртка над `replaceSync`) либо периодически переопрашивать. `[факт из кода]`: наличие `adoptedStyleSheets`-менеджера в динамическом движке Dark Reader подтверждается архитектурными описаниями (поиск 2026-09-22) и управлением стилями в `style-manager.ts`.

## 3. Каскад, специфичность, `!important`, inline-стили, псевдоэлементы, динамические классы `[факт по MDN + спец]`

Источник: MDN «Cascade layers», https://developer.mozilla.org/en-US/docs/Learn_web_development/Core/Styling_basics/Cascade_layers (получено 2026-09-22).

### 3.1 Cascade layers (`@layer`)
- Порядок слоёв **важнее специфичности**: внутри каскада сначала сравнивается принадлежность к слою, и лишь затем специфичность. Правило в более позднем слое побеждает любое правило в более раннем слое независимо от специфичности `[факт]`.
- Стили **вне слоёв** (unlayered) побеждают любые слоёные нормальные объявления `[факт]`.
- `!important` инвертирует порядок: `!important` более **раннего** слоя сильнее `!important` более позднего; `!important` вне слоёв слабее любого слоёного `!important` `[факт]`.
- Вывод для перекраски `[рек]`:
  1. Если приложение использует `@layer` (CSS-in-JS нового поколения, напр. некоторые сборки используют слои), можно объявить собственный слой **после** всех и побеждать без `!important`.
  2. Собственный не-слоёный `<style>`, добавленный в конец `head`, автоматически бьёт слоёные правила приложения по `!important`-нормальному каскаду.
  3. Против авторских `!important` — только свой `!important` (при равной специфичности выигрывает более поздний в документе/слое).

### 3.2 Специфичность и источник `[факт]`
- Классический порядок: `!important` > inline `style` attribute > ID > класс/атрибут/псевдокласс > тип/псевдоэлемент; при равенстве — позднее объявление `[спец]`.
- Инжектнутый в конец `<head>`/`<body>` `<style>` при равной специфичности побеждает по источнику `[спец]`.
- Универсальный рецепт `[рек]`: переопределять через **переменные** (`--color-bg: ... !important` на `:root`), а не через точечные селекторы — это снимает проблему специфичности для всего, что приложение завязало на переменные.

### 3.3 Inline-стили и динамические классы `[спец + рек]`
- Inline `style="..."` бьёт любые селекторные правила без `!important` → против них только `!important` в своём правиле либо перезапись `el.style.setProperty(name, value, 'important')` из скрипта.
- Приложение может **сбрасывать** наши inline-перезаписи через собственные MutationObserver/рендер-циклы (типично для React-приложений: при ре-рендере `style`-атрибут перезаписывается). `[рек]`: устойчивее переопределять каскадом (свои правила + переменные), чем править `el.style`; если правим `el.style` — готовиться к гонке.
- **Динамические/хешированные классы** (CSS Modules, styled-components с хешами, Tailwind) делают хрупким таргетинг по именам классов `[рек]`: опираться на структурные селекторы (теги, роли, атрибуты `data-*`, `aria-*`, позицию в дереве) и на переменные, а не на имена классов.
- Псевдоэлементы (`::before` и пр.) не читаются через `el.style`, но перекрываются обычными правилами вида `селектор::before { background: ... !important }` `[спец]`.
- Динамически меняемые цвета через `prefers-color-scheme`/`data-theme` атрибуты `[рек]`: перехватывать/принудительно выставлять атрибут темы или `color-scheme`, либо переопределять обе ветки.

## 4. Производительность и визуальные регрессии от сплошного сканирования `[рек + частично факт]`

### 4.1 Computed-style сканирование всех элементов (`getComputedStyle` по дереву)
- `getComputedStyle` форсирует вычисление стилей; массовый обход всего дерева на больших приложениях (Телемост — SPA с тысячами узлов, видеосетка) создаёт нагрузку и может вызывать лавину инвалидаций стилей `[спец]`.
- Чтение вычисленных значений в цикле **после** изменений чередуется с записью → layout/style thrashing `[рек]`.
- Главное ограничение `[рек]`: computed-style сканирование даёт снимок, но приложение продолжает менять стили → без постоянного наблюдателя результат устаревает сразу. Это вспомогательный (разведочный) инструмент, а не основа механизма.
- Практический вывод `[рек]`: не сканировать всё дерево на каждый кадр; сканировать точечно (видимые узлы, конкретные свойства) и кэшировать; основной механизм — правила каскада, которые «живут» и применяются браузером сами.
- `[факт из кода Dark Reader]`: движок использует `throttle` (импорт в `index.ts`) — мутации/обновления троттлятся, что подтверждает проблему производительности у реального продукта.
- Визуальные регрессии универсальных фильтров/инверсий `[рек]`: инверсия `filter: invert(1)` на корнях ломает фотографии, видео, графики, иконки-растры; двойная инверсия (инвертировать всё, затем выборочно вернуть картинки) — известный приём, но требует перечисления исключений.

### 4.2 MutationObserver-based обработка
- `[рек]`: обязательный компонент для живого приложения — новые узлы (модалки, сообщения, участники звонка) появляются после старта; без наблюдателя они остаются неперекрашенными.
- Стоимость: обход `addedNodes` и применение классов/переменных — дёшево; применение `getComputedStyle` в обработчике на каждый узел — дорого `[рек]`. Батчить в `requestAnimationFrame`/таймер, как это делает `throttle` у Dark Reader `[факт — наличие троттлинга в коде]`.
- MutationObserver не видит изменения `adoptedStyleSheets` и изменения текста существующих `<style>`-правил, сделанные через `CSSOM.insertRule` без замены текста `[спец]` → нужны обёртки в MAIN world.

## 5. Сравнение шести механизмов и гибридная архитектура `[рек]`

| Механизм | Сила | Слабость |
|---|---|---|
| Переопределение селекторов (`<style>` + `!important`) | Просто, живёт в каскаде, браузер применяет сам | Хрупко к динамическим классам/инлайн-стилям/псевдо-хешам; гонка с поздними правилами приложения |
| CSS custom properties override | Одно место правки; наследуется в Shadow DOM; не зависит от имён классов | Работает только если приложение уже использует переменные; иначе бесполезно |
| Обход правил стилей (document.styleSheets + переписывание) | Полный контроль, возможность пересчитывать каждый цвет (подход Dark Reader) | Cross-origin cssRules → SecurityError (нужен fetch с правами расширения); дорого; ломается при пересоздании таблиц |
| CSSOM-мутация (`insertRule`/`replaceSync`) | Быстро, без DOM-узлов | Приложение может перезаписать; не наблюдаемо через MutationObserver |
| Computed-style сканирование | Точная диагностика фактических цветов | Дорого, устаревает, не механизм применения |
| MutationObserver-обработка | Догоняет динамический контент | Не видит CSSOM-изменения и adoptedStyleSheets; требует троттлинга |

### Гибридная архитектура, подтверждённая практикой `[рек + факт о прецеденте]`
Зрелый прецедент — **Dark Reader** (open-source, https://github.com/darkreader/darkreader, арх. просмотрена 2026-09-22). Его динамический режим (`src/inject/dynamic-theme/index.ts`, `style-manager.ts`) комбинирует:
1. Обход и переписывание правил стилей (включая докачку cross-origin CSS текстом через `fetch` — `loadAsText`) `[факт из кода]`.
2. Обход и обработку Shadow DOM (`iterateShadowHosts`), наблюдение за позицией инжектнутых узлов (`watchForNodePosition`) `[факт из кода]`.
3. CSS-фильтры для изображений/видео там, где пиксели недоступны (`getCSSFilterValue`) `[факт из кода]`.
4. Троттлинг обновлений (`throttle`) `[факт из кода]`.
5. Пользовательские исправления для сайтов (fixes) — признание, что 100% автоматизации не существует `[рек]`.
- Стандарты, на которые опирается гибрид: CSS Cascading and Inheritance Level (layers, origin, `!important` порядок), CSSOM, Constructable Stylesheets/`adoptedStyleSheets`, Shadow DOM, CSS custom properties `[спец]`. Все эти механизмы — стабильные веб-стандарты, поддерживаемые текущими браузерами (2026).
- Рекомендуемая схема для Телемоста `[рек]`:
  1. Разведка: вычислить, использует ли приложение CSS-переменные/тему (`--*` на `:root`, атрибуты темы, `@layer`).
  2. База: инжектнутый `<style>` (в конец документа, вне слоёв или в собственный поздний слой), переопределяющий переменные + точечные правила с `!important` против инлайн-стилей.
  3. Наблюдатель: MutationObserver (батченный) для новых узлов + обёртки в MAIN world для `adoptedStyleSheets`/`CSSStyleSheet.replaceSync`, если приложение их использует.
  4. Тени: обход `shadowRoot` и инжекция тех же правил/переменных внутрь.
  5. Неперекрашиваемое (видео, растры, канвасы): `filter`/оверлеи точечно, либо сознательно исключить.
  6. Точечные fixes на известные проблемные места (как у Dark Reader).
